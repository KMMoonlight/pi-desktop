# Pi Component Mapping

The agreed standard-component desktop mapping and xterm fallback are complete for
the pinned SDK. [sdk-acceptance.md](sdk-acceptance.md) defines current completion
criteria. Arbitrary hidden component inference and terminal geometry are explicit
boundaries; broader unverified patterns below are not automatic pending work.

Ordinary resource/session transitions retain the workspace TUI, terminal, containers, original default editor/history, footer/provider and direct registrations. Extension-context subscriptions and session content reset independently; workspace teardown remains a hard retirement. See [runtime-lifecycle.md](runtime-lifecycle.md) and the current [grouped evidence](sdk-support.md).

Factories and tool/message render contexts receive one stable extension-facing TUI proxy per interactive generation. Method reads bind to the shared native renderer, including extracted and borrowed methods; callback functions such as `onDebug` therefore run with that renderer as their receiver. The proxy shares terminal identity, focus, registrations, overlays and mapping pause/resume. Desktop focus notifications carry the observed focus revision, surface instance and actual control action. They synchronize the actual leaf without first focusing a native overlay root or echoing a browser focus command. Explicit SDK overlay handles retain native activation/restoration semantics. Late notifications, retired instances and unavailable controls cannot replace newer SDK focus. Implicit browser focus clears superseded explicit requests; genuine DOM focus changes also cancel pending browser focus frames.

The shared application tree has seven original Pi Container roots: document, pending, status, above-editor widgets, editor, below-editor widgets and footer. The document contains header, resources and chat containers. Mapped factory roots and the default CustomEditor retain their original objects. Original user/assistant/summary/skill messages, complete ToolExecutionComponent rows, live/completed BashExecutionComponent rows and Spacer/ThemedText host notices populate chat; native FooterComponent and the shared FooterDataProvider populate the footer, and original indicators embed in the editor or occupy status. Header/resources, queues and string widgets remain Text bridges. Full tool rows occur once in the native application tree; desktop phase roots reuse their original callback children and mouse policy. Generic fallback text excludes image placeholders while the separate DOM image region is visible, preserving the full native row/result. Session-instance observers create original live bash rows for public executeBash/recordBashResult, retaining concurrent/deferred promotion identity. Host notices retain native chronology without SDK persistence. Direct registrations retain native order and separate occurrences; registrations/overlays survive creator retirement until removal or generation teardown. Global clear removes application containers; unrelated mounts do not restore removed roots. An extension's disposing parent retains native cleanup authority.

Cross-factory input follows the shared native focus after the single input-listener pipeline. Source browser text/selection never transfers to another focused component; forwarding joins asynchronous desktop input before replying. A late text acknowledgement updates its original field without reclaiming focus that a submission or listener moved elsewhere. Factory ownership context retains closure-held focus without inferring private component trees. Global stop makes all mapped regions and the default editor inert; start resumes their existing instances and pending renderer updates. Original invalidation traverses the shared application containers and native overlay stack. Retained handles still affect active peers; a retired generation cannot modify its successor.

This is a shared desktop mapping runtime, with a stable reference within one generation and an original default editor object. The complete original InteractiveMode built-in application component tree, reference continuity across renderer-mode replacement, exact terminal redraw/scheduling accounting, broader terminal protocols and arbitrary private ownership/geometry remain separate completion requirements. Current grouped evidence is in `sdk-support.md`; full SDK completion remains open.

Terminal presentation settings, color notifications/queries and window setters now share one registry/session generation. Hardware-cursor and clear-on-shrink flags are initialized from SDK settings and reach current and newly mounted factories. Color notification enablement applies across factories; direct subscriptions retain native live-Set order, duplicate/removal/insertion behavior and bare callback receivers. Closing or failing a factory does not remove global subscriptions. Explicit removal or generation teardown ends delivery. Window progress uses one last-writer state for direct TUI terminal calls, while independent opaque/PTY effect owners retain their separate lifetimes. Retained factory handles can still set the current generation's title/progress/flags; old generations cannot affect a successor. This supplies shared terminal state without claiming global TUI object/tree/focus/lifecycle identity.

Terminal input listeners and `onDebug` share one registry/session generation across mapped factories, ordinary desktop adapters, the default editor and native dialogs (including host-owned dialogs). A selected mapped/native editor synchronizes its valid browser context before the listeners run. The original live-Set registration, duplicate, insertion/removal, data transformation, empty-result consumption and exception behavior precede debug, extension shortcuts and recipient release filtering. Raw opaque/xterm components enter the same pipeline once; the actual PTY input channel remains separate. Listener edits to the selected control remain authoritative, including transformed releases without stale DOM context.

Direct `tui.addInputListener` subscriptions and `onDebug` are global registrations: retiring the factory does not unsubscribe or clear them. Extensions own explicit listener removal/debug replacement, just as with Pi's shared interactive TUI. Resource/session teardown retires the entire input generation, so old unsubscribe handles, late factories and callback assignments cannot affect its successor. The test presentation helper explicitly unsubscribes its own fixture listeners after completion; product mappings do not infer per-factory subscription ownership.

The preceding factory-scoped registration implementation has been superseded by the shared tree described above. Public mutation methods retain native returns, first-occurrence removal, array-replacing clear and mutation failures, while the InteractiveMode proxy binds their receiver to the shared renderer. Direct array changes are observed during rendering and teardown. Explicitly registering a factory return value still produces an additional occurrence. Global registered content renders at application width and contributes independently of a custom overlay's root bounds.

Registered subtrees share the existing type mapping, original input/mouse ownership, focus projection, pause/resume and disposal machinery. Ownership starts before factories finish. A late retired factory can register global children while its generation remains active; its returned root is still retired. Shared registered instances retained by another mapped root are protected from premature supplemental cleanup. Immutable original disposing parents retain their existing reservation rules and native direct-call behavior. Unobserved transient direct array mutations, arbitrary private ownership and universal DOM/caret identity across topology changes remain separate limits.

Overlay presentation removal is independent of component completion. Public `ui.custom` overlay `hide()` and direct `tui.hideOverlay()` remove their presentation without resolving the custom result or disposing its original component. Temporary `setHidden` state is separate from the visibility predicate; focusing cannot reveal a hidden or removed presentation, and restoring a capturing overlay restores its focus. A detached custom overlay ends on its own completion/cancellation. A detached direct overlay retains global lifetime until its mapping is explicitly closed or the generation ends. Both reject queued input, actions and stale layout reports. Current differential/browser/native evidence is recorded in `sdk-support.md`.

The default desktop path runs the original extension factory or renderer, retains its component instances, and maps Pi's component types into native DOM controls. It does not inspect extension names or source hashes and does not rewrite tool execution or extension handlers. It uses the pinned Pi SDK/TUI 1.0.0 for standard desktop mappings. Render-only custom components use xterm.js; raw terminal programs run in the SDK worker PTY. Known text components preserve Pi's styling and wrapping through semantic desktop text nodes.

Unknown wrappers that make one observable child render call at the same width compose the original wrapper output around that child's desktop representation. `componentReferences` discovers explicit data references in ordinary/Symbol fields, arrays, Map keys/values, Sets and nested plain records. Cycles and repeated aliases are visited once; original Map/Set iterators and data descriptors avoid holder accessors and candidate render getters. Instance-local probes record a snapshot before in-place changes and restore method descriptors, preserving callback-installed render replacements. Original wrapper handlers retain input ownership. Row metadata propagates through transparent/decorated wrapper layers, so enclosing transforms can retain original interactive descendants and native sibling controls. Focus requests follow the input-owner chain to their surface. Lifetime retention includes observed children after mapping and previously observed children still held through those collections when rendering skips them; hidden SDK updates survive, while actual replacement and teardown dispose original instances once. Multiple child calls, width changes and inaccessible/nonconfigurable/frozen methods keep the original xterm fallback. Closure-only/private/WeakMap references and arbitrary class-holder structures are outside this data-reference discovery. Empty unknown output maps to zero-height content. Current source/browser/native evidence is recorded at the top of `sdk-support.md`.

Opaque nonempty terminal frames register their explicit component descendants for input and lifetime without rendering additional desktop controls. Original descendant focus projects to its visible xterm; a closure-held unregistered focus target projects when its surface has one terminal frame. Terminal data uses Pi's raw keyboard path, including original Ctrl+A line-start behavior. A frame without `handleInput` dispatches to the current Pi focus; an existing wrapper handler keeps its ownership without replacing that focus. Listeners can redirect, consume or clear focus during the same key. An explicit clear also prevents a subsequent unscoped input call from selecting an implicit first control. Pi focus remains global across opaque regions: clicking another emitter does not move it unless an original handler requests focus. Standard native controls keep their existing selection behavior.

Previously observed children are also probed when a wrapper moves their references into a closure, WeakMap or JavaScript private field. Actual original render calls establish current ownership; the mapper does not discover arbitrary private references or invoke render getters. A changed-width call retains the xterm path while preserving the original focused instance and lifetime. A later observable same-width call can restore desktop controls, including SDK changes made while the component was terminal-rendered. Inaccessible/nonconfigurable transitions, initial private ownership and shared appearances remain unproven.

SDK focus requests for composite components without a leaf action focus their own `data-component-action` element with `tabIndex=-1`. The composite's original keyboard handler remains the input owner. Readonly SettingsList and a Container with its own handler have desktop/narrow browser and native verification; a focus request does not implicitly select a child input.

`component-disposal.ts` owns cleanup independently of writable instance properties. It preserves locked/accessor/nonextensible disposal descriptors and the original receiver; configurable readonly and inherited data methods can use an instance guard. Accessor callbacks are resolved only at cleanup. Original disposing parents retain authority over noninterceptable descendant methods, avoiding an extra desktop cleanup call. That delegation is scoped to a release pass, so an immutable cached child left alive by its original parent can be reused and cleaned later. Descendants are claimed before reading a disposal getter, preserving side effects even when it throws. Replaceable methods retain exactly-once guarding and sibling cleanup after exceptions. An observable still-retained immutable descendant defers its original owner tree until retirement, so renderer replacement cannot prematurely dispose the live control. Arbitrary inaccessible ownership and multiple original immutable disposer owners remain verification limits. Source/browser/native evidence is recorded at the top of `sdk-support.md`.

Cleanup records belong to a mounted lifecycle. Known desktop guards unwrap through private WeakMap metadata across factories; retirement restores original methods or an active peer guard and preserves callback-installed replacements. Each installed guard retains its original callback snapshot. Replacements get a new guard, so an extension wrapper can call the guard it captured before replacing the method. Node `AsyncLocalStorage` preserves each cleanup's original mounted records, descendant graph, retained components and delegation across microtasks, timers and awaits. That saved callback runs in its original cleanup scope, including a callback captured from a retired mount, without consuming a successor lifecycle. Guarded callbacks retain their original return values/Promises and are memoized to prevent recursive/duplicate calls. Outside that chain, captured retired guards remain inert. Peer restoration generates a guard for the current replacement. Reusing the same object in a later factory starts another cleanup lifecycle. Reentrant releases take fresh current snapshots and keep independent invocation chains, including factories sharing the same original method. Post-mount freezing retains the frozen descriptor, with known original callbacks available to desktop cleanup. Component release invokes cleanup synchronously, preserving Pi's non-awaited close contract. Repeated custom dialogs and overlapping header/footer Input factories have focused source/browser coverage. This does not establish arbitrary shared native/terminal appearances, unrelated/external async-resource boundaries or every direct call through a method frozen around an old guard.

Custom dialog close resolves the original result before abort/disposal, and continues to invoke original cleanup synchronously. Abort listeners are removed directly on settlement; authorization ownership observes the original result Promise before callers run. This preserves public Pi custom-UI result versus disposal-continuation ordering without adding a returned cleanup chain. The differential reference invokes unchanged Pi InteractiveMode with the same original SDK UI-prompt wrapper as the desktop. Native/opaque roots, plain/overlay dialogs, synchronous cleanup/errors and up to 32 continuation steps have source coverage; real-extension browser/native evidence is recorded in `sdk-support.md`. Factory failures preserve their original rejection and retire signal listeners. A throwing desktop completion callback still aborts, disposes and publishes removal. This does not prove every reentrant asynchronous presentation or unrelated/external async boundary.

Transaction ownership is per control. A callback changing another control retires that sibling's browser context, including when the callback is triggered by keyboard, submission or native mouse input. Mapped factory `tui.stop()` now pauses its desktop surface: it releases mouse capture, makes the retained presentation inert, suspends keyboard/mouse/action dispatch and freezes rendering. `tui.start()` resumes the same component instances, invalidates their caches and displays current state. Calls on retired factories cannot resurrect them. Pausing from inside an input callback also suppresses editor-response updates. Overlay views share the pause state and retain their last measured height. Renderer updates received while paused are deferred until resume. These are instance-local desktop lifecycle implementations; SDK classes and global prototypes are unchanged.

Terminal ownership is supplied by the separate PTY supervisor. Pi's unchanged `interactive-shell.ts` can write ANSI and start inherited-stdio children; xterm.js handles their display and input. Standard mapping retains desktop pause/resume. See [terminal architecture and limits](terminal-compatibility.md) and [SDK support evidence](sdk-support.md).

Exceptions in invalidation callbacks are reported independently; a callback that closes a pending surface cannot cause it to reappear.

Explicit `tui.setFocus()` calls carry the original component identity and a focus revision to the owning desktop surface. A failing disposer reports its error while remaining child/editor cleanup continues; it does not replace an original render failure or discard a completed dialog's result.

Browser authorization notices from a custom UI follow the semantic authorization link in that UI's own surface. After the link has been presented, removing it dismisses the browser request without sending a cancel key to the replacement controls. The original asynchronous operation continues and presents its own result; closing this request does not mean token exchange succeeded. This observation uses link destinations rather than extension names or error text. A URL never exposed as a mapped link falls back to credential persistence or scope closure.

Native selection shortcuts first reach the original Input/Editor handler. Text or cursor changes take precedence over the desktop fallback. An unchanged result retains desktop select-all, copy/cut and Shift selection; the host's default clear/copy actions defer when a CustomEditor has a selection. Extension-installed actions retain ownership. A void handler with no observable state change cannot communicate consume intent; explicit SDK terminal-input consumption is honored before this path. This boundary is not proof of arbitrary custom-handler equivalence.

When replacing a focused control leaves browser focus on `body`, the keyboard bridge routes keys to the sole mapped modal's original input handler. This preserves Escape navigation through a component's nested menus instead of letting the desktop modal close prematurely. The fallback requires exactly one DOM dialog and a mapped surface accepting keys; it does not infer an owner across multiple dialogs. Desktop/narrow browser regressions exercise returning from a SettingsList submenu and then closing through its original callbacks.

Input and mouse editor transactions include the same selection revision used by component snapshots. The desktop acknowledges that revision even when the response arrives before its snapshot, so a delayed snapshot of an already-confirmed insertion cannot collapse a newer native range selection. Subsequent selection revisions still apply normally. This retains the original input handlers, text revision, selection mapping and undo behavior.

Text-control layout reports its LTR/RTL direction as well as caret positions. The original Editor/CustomEditor input handler still receives each key; standard horizontal movement uses that direction, and a selected range collapses to its measured visual edge without stepping past it. Single-line Input uses unwrapped browser geometry, scoped direction-aware keybindings and scoped cursor writes after Pi matches a movement command. Its original handler receives unchanged input data, and property descriptors restore on success or exceptions. A consuming handler can retain the range. Default-editor commands, remapped keys and frontend Shift-selection follow the same presentation direction. Logical deletion stays separate. Browser reference cases cover English/Arabic/Hebrew mixtures in default, custom and dialog textareas and single-line Input; arbitrary bidi affinity remains separate verification work.

`Text` and `TruncatedText` source styling maps to structured DOM spans using an SGR state normalizer, Anser's parser and Pi's own indexed-color conversion. Standard/bright/256-color and RGB colors, foreground/background resets, bold, dim, italic, underline, strikethrough, reverse, hidden and blink decorations retain separate lifetimes. Repeated style enables are idempotent, so one reset clears the style. Semicolon and colon RGB/palette colors are supported. Underlines support solid, double, wavy, dotted and dashed styles with independent colors; overline and strikethrough retain their own solid, foreground-colored lines. Malformed color groups and unsupported color-space IDs preserve the existing style. Reverse styling uses the inherited desktop foreground/background when ANSI leaves a color unspecified. Blink honors reduced-motion preferences. Truncated text retains only its first source line and uses native ellipsis; `Text` expands tabs to Pi's three spaces.

`ScrollView` retains `hidden`, `auto` and `always` scrollbar modes. The native viewport uses the original visibility/activity state, including Pi's transient hide timer and `setScrollbarActive()` lifetime. Track/thumb callbacks receive Pi's original glyph arguments and their foreground colors style the native scrollbar; character artwork remains native to the platform. Always mode reserves a scrollbar even for short content; hidden mode removes it without preventing scrolling. Native scrollbar hover activity uses the same original method through a validated component action. Disposal clears the original hide timer.

`Image` retains its declared dimensions and aspect ratio. Its original `maxWidthCells`/`maxHeightCells` and default limits map through the desktop viewport's logical units (8 px per column, 20 px per row), bounded by the allocated component width and the available DOM width. Native image loading errors display Pi's original `imageFallback()` text through the instance's `fallbackColor` callback and structured styles. Updating the original image options or source and invalidating it updates the same mapped component; a new source retries loading after failure. Kitty/iTerm image IDs and escape sequences stay in the original instance and are not used for desktop drawing.

OSC 8 HTTP/HTTPS, mailto, tel and file links use Pi's original parser and a shared desktop URL validator/opener. Markdown link metadata uses the same validation, preserving original theme callbacks. URL syntax is normalized consistently across backend and client; literal control characters, empty mail/phone destinations and executable web schemes stay non-clickable. Tauri enables both the opener command and its default URL scope. Email/phone activation is tested with intercepted opener calls; actual HTTP opening is tested against a disposable local page through the OS default browser. Other terminal instructions are discarded rather than executed, and all source content is rendered as React text. `Text.customBgFn` and `Box.bgFn` supply native background colors across content and padding. Markdown default backgrounds cover its native content/padding area; text defaults are applied through Pi's original inline renderer, so resets inside code and nested formatting retain their effect. Original component callbacks can change the source text and invalidate the desktop presentation normally.

Custom application protocols (for example `vscode:` and `obsidian:`) share the same component link mapping and user-click dispatch. The native command validates the URI again before invoking the system default protocol handler; it does not widen the plugin's URL scope or select an application on the user's behalf. Relative paths, bare Windows paths, empty destinations, controls, whitespace, and script/embedded-page schemes (`javascript:`, `vbscript:`, `data:`, `blob:`, `about:`) are rejected. Original labels, theme callbacks and encoded arguments are retained. Whether a handler is installed is an OS concern; launch errors use the same inline link feedback.

File links use Node's `fileURLToPath` on the backend and Tauri's scoped default file opener. Decoding preserves Unicode, spaces and literal percent/hash characters, rejects encoded path separators and NULs, and follows the host platform's path rules. Files and directories may be outside the workspace, matching a user-activated system file link; the workspace file browser retains its existing boundaries. URI query/fragment parts are not part of the filesystem path and are not interpreted as editor line commands. Ordinary transcript Markdown and mapped Pi text/Markdown share link activation and inline failure/retry feedback. Browser previews show that file opening requires the desktop application. Stale failures cannot attach to a link whose destination has changed. Transcript Markdown uses stable renderer identities so unrelated message/snapshot updates retain pending link errors. Before native file dispatch, `files.resolveLink` with `mustExist: true` checks the target with Node stat; a missing file/directory yields an inline error instead of relying on the detached OS launcher to report it. The default resolver remains pure path conversion when this option is absent.

Markdown uses the token tree parsed by its original Pi instance, including strict strikethrough, LaTeX, streamed partial fences and the original source options. Pi's original token/inline renderers apply heading, link/URL, code, emphasis and strike themes; code blocks retain `highlightCode`, indentation and border callbacks. Lists retain ordered start values, optional original markers and task markers; tables retain alignment and original header styling. Quotes and horizontal rules map border colors to native borders. Scoped link metadata gives validated external link labels native link actions while retaining the original theme callback; the instance's theme is restored even when rendering fails. Collected weak token caches are rebuilt through the original instance. The frontend renders semantic DOM blocks and structured text spans, without reconstructing controls from terminal lines. Non-styling character-art additions made by border theme callbacks are not converted into new desktop controls.

Markdown source transforms receive their allocated component width after ancestor and component padding. A regression verifies nested Box/Markdown transforms when a percentage-width overlay narrows from 20 to 12 logical columns, producing content widths of 14 and 6 rather than the full desktop viewport width.

Control captions carry structured text runs. Input prompts retain source colors; `placeholderStyle` transforms the actual placeholder and supplies native placeholder CSS, while editor and DynamicBorder callbacks supply native border colors. SelectList labels use the original display-value method and selected-text theme; explicit `truncatePrimary` callbacks receive allocated content width, primary-column constraints, original item identity and selection state. Selected descriptions, empty-result themes and scroll counters retain their callbacks. SettingsList label/value themes receive the original selected flag; its cursor, current-item description, filtering and empty-state theme are represented in desktop controls. Actual option values and setting IDs remain separate from displayed/transformed labels.

Loader message styles and indicator colors come from their original functions. Explicit custom indicators expose their current source frame as structured desktop text, while the original timer and cancellation/disposal remain active. BorderedLoader maps its original children, including spacers and colored DynamicBorders. Single-style options and placeholders use native browser controls. Mixed styles, hyperlinks or blink use structured placeholder overlays and desktop selection menus/listboxes. Original values and actions remain separate from displayed text; menus rendered outside the component's DOM subtree retain their original surface and instance for keyboard and pointer routing. Link clicks retain their native link action without selecting an option. Hidden text and independent style resets retain their source semantics. Unstyled native options use their default control color rather than inheriting the selected option's color, for both collapsed selects and visible listboxes.

`setStatus`, `setWorkingMessage` and string-array `setWidget` use the same structured text parser and link handler. Styles continue across widget lines until their original reset; literal HTML remains text and terminal instructions remain inert. Raw strings stay available to native SDK callers and footer data providers, while `extensionUI.textPresentation` contains the desktop text/runs. Widget placement changes, factory/string replacements, removal, reload and session replacement use the existing host lifecycle.

Rich selection menus retain Pi's foreground and weight resets rather than inheriting the UI library's selected-item text color. On mount and source selection changes, the list scrolls its selected option into view; keyboard focus follows only while it already belongs to that list. The same behavior serves collapsed menus and permanently visible lists. Browser/native workflows exercise 24 original options starting at item 20, movement in both directions, original values, callback counts and confirmation.

Editor completion confirmation belongs to the original editor rather than an ephemeral suggestion-list instance. Native button commands follow queued keyboard input; a delayed confirmation after completed Tab input does nothing. The textarea descriptor exposes this command through `completionAction`, so retiring a suggestion list does not invalidate an already issued confirmation.

Editors receive browser-measured visual rows and grapheme caret positions through the shared input context. Scoped instance geometry lets the original Pi handler perform Up/Down, configured navigation, history and paging against desktop wrapping and proportional fonts. Consecutive vertical moves retain their pixel column, and pages use the textarea viewport with Pi's minimum five-row step. Shift selection uses the same measurement. Default, custom and dialog editors have browser-reference regressions at desktop/narrow widths, plus the native `--editor-navigation` workflow. Pi's boundary/history semantics remain active; bidi caret affinity and unusual custom geometry are not claimed as equivalent to a plain native textarea.

Mapped text insertions capture their selected range when the native input event arrives and display provisional text without dispatching another edit. Original handlers still run in order; consecutive insertions rebase through their results and final acknowledgements preserve newer drag selections. A delayed-pointer browser regression and native `--pointer-replacement` workflow repeat immediate replacement/drag selection 20 times and wait for pending input/pointer replies before checking the final text and range.

Queued navigation measures the editor when its input transaction executes. Default, custom and dialog editor regressions hold an earlier navigation acknowledgement, resize between desktop/narrow widths and queue Shift selection, then compare the resulting range with a native textarea. The same resize workflow runs in native `--editor-navigation`.

Theme APIs expose Pi's `system`, `light` and `dark` themes even with a custom resource loader that disables theme discovery. Initial binding and session replacement apply the saved setting; an absent setting uses `system`. Named changes persist settings, while direct `Theme` instances do not. Active theme changes update Pi's global theme helpers and desktop CSS tokens together. The desktop reports its system appearance before initialization and on media-query changes. Automatic light/dark pairs and the named system theme follow those reports; fixed names and in-memory instances keep their selection. The settings appearance control uses the same SDK theme API and retains its system selection while appearance changes.

Named custom themes watch their actual source file, including project/resource paths and filenames different from their declared names. Directory watching survives atomic file replacement. Pi's original JSON validator and theme loader reject malformed or invalid files while preserving the last valid colors. Theme changes, resource reload, session replacement and disposal release old watches and delayed reloads. Settings, trust, package and configuration reload actions share the desktop reload lifecycle; project theme settings apply only while the project is trusted. The system theme uses Pi's appearance-based fallback colors because there is no terminal palette to query.

Mapped editor paste blocks have a collapsible native preview, a read-only full-content field and copy/remove commands. Registered markers are atomic caret/selection spans, using Pi's original segmentation and paste expansion. Partial selections expand to the marker boundaries; an interior caret snaps to the marker start. Literal marker-looking text without a registered paste remains editable. Removal uses the original editor undo transaction, and stale controls cannot remove a renumbered replacement. Preview inputs remain outside the extension key bridge.

Native text insertion containing control bytes is encoded as bracketed paste before invoking original input listeners and handlers. Literal newlines therefore replace the active range and enter Pi's multiline insertion engine, rather than its key parser or single-line character insertion. Pi retains line-ending/tab normalization, paste compression and original callbacks/undo. Committed composition text uses the same encoding; default native-control fallback decodes framed text before insertion. Browser regressions cover multiline fill, cross-line ranges, consecutive insertion, large-paste reads/undo, original subclass transformations and listener consume/replace in default, custom and dialog editors, plus CDP multiline composition. The same workflow runs through native `--input-replacement` and both broader native modes.

Single-line `Input` range changes save Pi's original value/caret before removing the browser range, and retain one undo snapshot across the original handler. Scoped snapshot methods are restored after success or errors; replacements made by the original handler survive. Integration/browser/native regressions cover replacement, newline/tab normalization, deletion, undo, exception cleanup and original submission.

Selected Backspace/Delete first reaches the original `handleInput()`. A handler that consumes the key retains its text and selected range. When the handler delegates to a deletion method, the bridge reduces the range to one original grapheme and calls that original method within one undo transaction. This retains synchronous change callbacks and the original deletion method's side effects. Instance method descriptors are restored after success/errors; replacements made by a handler survive. Integration cases cover Unicode, line breaks, callbacks, undo and exceptions inside deletion methods. The shared browser/native input-replacement workflow also checks ordinary extension subclasses and consumed keys.

IME provisional text stays in the desktop control. Only committed text reaches the original component and input listeners, against the pre-composition selection. Cancellation restores that selection's original text. Consecutive commits use the previous handler's actual result, preserving subclass transformations and listener consume/replace semantics. An earlier acknowledgement cannot change a newer composition's provisional text or clear its active flag. Pi retains its original undo coalescing. Regressions pass for both final-input event orders, selection replacement, cancellation and consecutive/overlapping compositions at 1440px and 390px and in native WebView2. Real OS input methods remain a separate validation item.

Ordinary typing and paste immediately after a composition commit use the same input queue and read the resulting text/selection after preceding transactions. Final-input suppression distinguishes a duplicate commit from legitimate repeated text by inspecting the DOM value. Chromium CDP composition/input cases supplement synthetic event tests for cancellation, transformations and undo. CDP's composition-end event is untrusted, so these cases still do not establish real OS IME compatibility.

Each mount has a distinct instance ID. Obsolete actions cannot affect a replacement. Tool renderers receive their original shared state, `lastComponent` and `invalidate` callback. Updates retain reused components and release retired instances; temporarily invisible layout children remain alive. Original cleanup is guarded once per mounted lifecycle, including parents that dispose their children. Retirement restores methods for later factories; loaders, completion requests and footer watchers are released on teardown.

Pointer regions reuse Pi's mouse dispatcher and retain its exact child capture target across press, drag and release, including motion outside the region. Standard-component subclasses with custom mouse handlers also receive a mapped region automatically. Nested regions dispatch through their original Pi hierarchy once, so unhandled child events reach their parent without duplicate callbacks. Handled presses retain their original target even without explicit capture; unhandled presses release temporary DOM capture once the asynchronous decision arrives. Pi click counting is preserved, and dragging or cancellation does not synthesize a click. Focus respects delegating containers and overlay owners, and late responses cannot override a newer pointer or keyboard interaction. Explicit `render: false` results do not unconditionally publish a new view; retired components lose captures and focus.

The desktop keeps each gesture's native control, hit ancestry, last event and asynchronous capture decision separately by `pointerId`. Releasing or losing one pointer does not clear another gesture. Native controls retain their selection guard until all their active pointers and pending replies settle. Non-native pointer regions disable browser touch panning so Pi receives their drag/release events. Chromium CDP touch regressions cover simultaneous rejected captures with delayed Pi replies, releasing one of two captured pointers before an outside drag, and two pointers on the same native input. These run at desktop/narrow browser widths and in mapped-component/native workflows; they do not establish compatibility with every touch device or mobile keyboard.

Native input, textarea and list controls forward their pointer events through any mapped mouse ancestors, including `MouseRegion` and container subclasses. The bridge converts browser caret/option identity into Pi's original mouse-dispatch coordinates and retains concrete child capture targets. Browser range selection remains native unless Pi explicitly captures the pointer. Original handlers may change text/caret even with `render: false`; their editor transactions commit before subsequent queued input. Mouse-sensitive `SettingsList` instances use desktop cycling/submenu buttons, so the original handler activates a setting exactly once. Keyboard activation uses the original setting action. Selection synchronization updates caret state without reclaiming focus from a newer overlay.

Mapped component occurrences carry distinct tree keys, including when one original instance appears in multiple positions. The desktop sends the actual DOM hit ancestry and component bounds, and retains the press ancestry while dragging. The backend validates this path against the current component tree, then scopes instance mouse dispatch to its selected children and local coordinates. Pi still normalizes the original handler results, capture targets and delegated focus. Scoped layout getters keep synchronous refreshes inside an extension callback from changing the current event's route; writes made by the original render are retained afterwards. Original instance descriptors are restored in `finally`, including when a handler throws, and retired occurrence keys are released. No Pi prototype or installed source is modified. Older native-control payloads use Pi's stack size allocator for horizontal/vertical child frames without overwriting DOM-fed scroll measurements.

Direct `tui.showOverlay()` calls use the same component mapper, including stacked overlays created before an asynchronous factory returns its main component. The original Pi overlay stack and focus handles remain active; desktop surfaces expose positioning, visibility and input. `hideOverlay()`, handle hiding, explicit focus/unfocus and parent teardown close or update the matching desktop surface. An overlay's inputs route to its own original component rather than the parent's input handler.

Overlay widths, percentages, anchors, offsets, margins and height limits use Pi's original `TuiMainScreen.resolveOverlayLayout` implementation with the logical desktop viewport. The original component renders at the resolved overlay width and supplies the initial height. A `ResizeObserver` then reports the visible desktop content height in logical grid units so native control heights participate in positioning. Measurements carry the mounted instance and layout identity; replies from replaced/hidden overlays or older viewport/options cannot change current bounds. Width also propagates through component composition: Box padding and ScrollView content widths are applied, while stacks use Pi's original size allocator. Zero-width HStack and zero-height VStack entries map to noninteractive zero-size placeholders, preserving stack gaps and original component instances. ## Compatibility Limits

- Pi has no public native component descriptor API. `backend/component-runtime.ts` isolates version-dependent component field access and the SDK keybinding/footer implementations. Missing required fields fail explicitly. SDK/TUI upgrades require bridge validation; this is not an automatic future-version compatibility guarantee.
- An arbitrary component whose only structure is `render(width): string[]` cannot be inferred as semantic desktop controls. Such roots and nested components use the generic xterm fallback with original keyboard, mouse and completion callbacks. All standard type overrides retain added lines and empty frames through a generic comparison, and native text controls also retain changed editor-border labels, including inherited and instance Editor/CustomEditor helpers. The four passive types retain replacement/removal/interior insertion; independent canonical baselines also preserve Markdown/Box cache additions. Documented vertical Container/Box/VStack frames retain whole native children in their rendered order and preserve surviving text fragments. Direct Input/Editor/CustomEditor/SelectList/SettingsList replacements and transformations retain original input ownership; parent-transformed partial interactive children do so recursively through identifiable vertical ranges and HStack rectangles, including ScrollView's original content child and observable same-width wrapper layers. HStack gaps retain documented drawing and styled blanks. Unattributable multi-child changes, wrapper transforms without observable child ownership, arbitrary delegated width/position changes, arbitrary column relocation/resizing, indistinguishable moved frames, additional helper/cache patterns, arbitrary interior geometry and per-character styling inside a textarea remain implementation or verification boundaries.
- DOM flow, font metrics and wrapping differ from terminal cells. Standard text source styling, Text/Box backgrounds, Markdown theme/default styles, control captions, options/placeholders, status/working text and string widgets map to desktop styles as described above. Supported custom frames retain their original drawing and opaque components use xterm. The structured SGR mapper covers colon colors, underline styles/color, overline and reset groups; unsupported terminal-specific drawing remains a boundary. Exact terminal cursor/page geometry and custom scrollbar artwork do not retain their original appearance. Native control hits use caret/option identity; other hits use desktop component bounds. Horizontal/shared occurrences, vertical gaps, clipped scroll children, synchronous refresh and boundary-crossing capture are covered by regression tests. Pi's overlay resolver preserves its layout rules in desktop logical units; it does not reproduce terminal glyph dimensions or arbitrary custom container drawing. Additional physical touch devices, browser-default gestures and native-control selection handles have no universal validation guarantee.
- Pi's editor retains its terminal editing engine and paste-marker model. The native textarea supplies range selection and paste previews. SDK reads, accepted prompts/history and editor restoration expand large-paste markers. Text synchronization and selection replacement preserve paste bodies, with atomic original undo and synchronous callbacks. Desktop selection typing/paste/deletion, registered marker boundaries, paste preview commands and synthetic IME compositions have regression coverage. Real OS IME remains unverified; every third-party selection/undo and editor combination is outside the universal compatibility guarantee.
- The separate runtime pins its SDK independently of a globally installed Pi CLI. Upgrading that CLI does not change the desktop's SDK.

`tests/fixtures/component-library.mjs` is installed as an ordinary renamed extension, with no dedicated adapter. Integration tests exercise all 17 pi-tui component constructors and the SDK's `CustomEditor`, `BorderedLoader` and `DynamicBorder`, original callbacks, footer data, remapped confirmation keys, setting IDs with colons, submenus, custom editor input/completion, narrow viewport visibility, scroll state, loader cancellation, resource reload and disposal. Direct-overlay tests cover stacked inputs, original focus handles, responsive visibility, parent cleanup, factories awaiting overlay input and delayed selection from a previous overlay. Mouse tests verify concrete nested capture targets, delegated container/overlay focus, keyboard routing after child removal, render flags, implicit retention, click counts and cancellation. Native-control cases cover original subclass handlers, ancestor bubbling through padded containers, mouse changes with `render: false`, retained native range selection, single setting callbacks, colon IDs and stale control rejection. Additional renderer tests verify component reuse, shared-child lifetime, explicit invalidation and suppression of repeated failures from unchanged unsupported renderers. Browser and native WebView2 workflows exercise actual DOM input, native selection, settings, completion, scrolling, explicit native capture outside bounds, single nested dispatch and image loading, plus nested overlays before a factory returns; browser coverage includes desktop and narrow widths, delayed capture decisions and focus response races.

Layout regressions also cover right-column native handlers, distinct shared-instance occurrence paths, captured motion outside a horizontal layout, clipped scroll hits without resetting scroll state, vertical gaps falling back once, malformed hit ancestry, synchronous original renders, handler replacement and exception cleanup. Browser workflows at 1440px and 390px exercise horizontal native inputs, shared-component clicks and wheel events, and scrolled children using actual DOM hit paths. The packaged native WebView2 workflow also checks horizontal inputs, shared-instance clicks and clipped scroll wheel events.
