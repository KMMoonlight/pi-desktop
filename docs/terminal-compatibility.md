# Terminal support

Current completion and verification scope is defined by
[sdk-acceptance.md](sdk-acceptance.md). The shared application content and
[invocation options](invocation-options.md) are now integrated. Earlier statements
below that these categories remained open are historical. Unsupported xterm
protocols, arbitrary private geometry and untested environments remain explicit
boundaries; they are not universal compatibility requirements.

One original Pi stable TUI reference and terminal belong to each workspace interactive lifetime. Ordinary reload/new/switch/fork/import retain them and their direct registrations; session UI/content reset separately. Workspace replacement and shutdown retire that lifetime. See [the lifecycle contract](runtime-lifecycle.md). Factories and render contexts share native focus, child registrations and overlays. Standard components map to desktop controls; opaque frames and raw programs retain xterm.js/PTY paths. Seven application roots contain original user/assistant/summary/skill messages, complete ToolExecutionComponent rows, live/completed BashExecutionComponent rows, FooterComponent/shared provider, status indicators and Spacer/ThemedText host notices. Full tool rows retain original callbacks, state and children; desktop phase/image projection does not change native result data. Session-instance bash observers retain concurrent, pending/deferred promotion and cancellation behavior while preserving SDK options/callbacks/results. Notices do not enter SDK messages/JSONL. Original header/resources, pending queues, bounded string widgets and specialized notice components now populate the shared native tree; see application-content.md and conversation-notices.md. Original indicators embed in the CustomEditor border or occupy status, retaining timers across editor moves and stopping on retirement. Start/stop pauses/resumes mapped regions and the original default editor. Leaf/revision focus guards retain native overlay semantics. Arbitrary private application geometry and terminal protocols beyond xterm support remain compatibility boundaries. Renderer-mode continuity and native lifecycle/redraw accounting use the original Pi implementation; see [the renderer contract](renderer-modes.md). Current category evidence is in sdk-support.md.

TUI terminal presentation state is generation-wide: cursor/clear-on-shrink flags, color notification enablement/listeners, pending queries and direct title/progress setters are shared across mapped factories. Closing a factory retains those registrations and queries; generation teardown cancels them and rejects stale writes. Direct progress setters use last-writer semantics, independently of raw opaque/PTY OSC effect owners.

The Windows supervisor excludes the first ConPTY initialization title only when it matches the observed clear/reset signature and worker executable path. This prevents an initial cursor write from overwriting a direct SDK window title; subsequent explicit path titles and ordinary OSC titles remain accepted. Grouped source/browser/native results and the initialization fixture repair are recorded in `sdk-support.md`. Other ConPTY initialization layouts are not universally verified.

Factory TUI input listeners and `onDebug` use a session-wide desktop pipeline. Registrations from headers/footers/widgets can observe and transform input in other factories, the default editor, native dialogs and opaque xterm components. Direct registrations survive their creating factory until explicitly removed or the input generation retires. The selected native control's valid DOM context is synchronized first; transformed release events cannot import stale DOM text. Debug runs with the underlying shared renderer as receiver, after listeners and before extension shortcuts/recipient release filtering. Actual PTY `ProcessTerminal` input ownership remains separate. Current grouped evidence is in `sdk-support.md`.

Original components registered directly with `tui.addChild()` use a global region with the same desktop mappings and opaque xterm fallback as returned roots. Native order, duplicates, shared-instance input/focus and explicit lifetime remain intact. The proxy binds extracted/borrowed mutation methods to the native renderer. Global `clear` removes application containers as well as direct children; direct overlays remain in their native separate stack. Grouped source/browser/native evidence and remaining limits are in `sdk-support.md`.

The user explicitly chose xterm.js for terminal support. Pi 1.0.0 remains unmodified. Standard Pi components still map by component type to desktop controls; no extension name or source hash selects the terminal fallback.

Opaque component xterm keyboard input now joins the desktop's ordered global/factory listener path, preserving press/repeat/release metadata and the original receiver's `wantsKeyRelease` filtering. Captured composition and paste have one shared delivery path; xterm cannot duplicate them through its own helper handlers. The PTY panel retains its original xterm input. Pi 1.0.0 still cannot match phased F-key identities through `matchesKey`/`parseKey`, although raw phase flags are available. Ordinary F-key presses retain legacy matching, and phased function keys do not become printable private-use characters. Current grouped evidence and exact limits are recorded in `sdk-support.md`.

Raw title/progress/clipboard effects now use xterm's OSC parser and the desktop host. Supervisor output indices and component data revisions prevent repeated clipboard writes on history replay and live component reload. Effect delivery stays independent of parsing/PTY input while the SDK is synchronously blocked. Clipboard writes validate UTF-8/base64 and Pi's original size cap; queries and non-clipboard selections are not supported by this write bridge. Current grouped source, browser, build and native evidence is at the top of `sdk-support.md`, including the recording-provider clipboard verification limit.

Native and frozen opaque xterm overlays now preserve Pi's separation of presentation removal and completion. `hide()` removes the presentation without resolving the custom result or disposing its original component; temporary hiding/restoration preserves original input and results. Detached components remain owned until completion/cancellation/parent teardown and cannot receive stale queued input or layout reports. Current differential, source, desktop/narrow browser and native evidence is recorded at the top of `sdk-support.md`; earlier verification counts in this document are historical.

## Architecture

- `backend/terminal-host.ts` runs the SDK worker inside a real `node-pty` PTY (Windows ConPTY). The outer process owns terminal input, resize, output and worker cleanup independently of the SDK event loop. This is essential for original extensions using blocking `spawnSync(..., { stdio: "inherit" })`.
- Shutdown joins original SDK cleanup and actual worker exit. HTTP drains existing action/SSE responses before supervisor exit; native/stdio shutdown events join disposal before protocol termination. Startup exit rejects its handshake waiter promptly, and an authenticated disconnect rejects pending operations and clears the closed socket. Terminal history stays available after a connected worker exits until explicit supervisor shutdown. Cleanup failures produce an error exit. Current grouped source, Rust and desktop evidence is at the top of `sdk-support.md`.
- SDK messages use a separate authenticated loopback connection. Ordinary output, ANSI sequences and JSON printed by an extension cannot become SDK protocol packets. Native Tauri still talks to the supervisor through its existing private channel; browser preview uses authenticated HTTP/SSE. Socket resets emitted through the readline interface reject pending operations and close that connection without terminating the PTY supervisor; terminal snapshots remain available.
- `src/TerminalPanel.tsx` uses `@xterm/xterm` and `@xterm/addon-fit`. Extensions handing off the terminal or calling raw terminal APIs open the panel; ordinary startup logs do not steal focus. input, Ctrl+C and resize reach the PTY. Output history is bounded to approximately two million characters, with sequence numbers to avoid replay duplication. Hiding the panel does not kill the SDK. Its persistent DOM host moves inside extension modals so backdrop/focus handling does not block real mouse input.
- `backend/detached-tui.ts` supplies original Pi `ProcessTerminal` operations when hosted in the PTY. Explicit raw terminal listeners stop when their component is disposed. Desktop title/progress retain their native window presentation. In-process SDK tests and legacy `--stdio` do not allocate a PTY.
- `backend/component-mapping.ts` maps unknown render-only components to an xterm view, preserving the original object, `render`, `handleInput`, listeners and completion callbacks. Standard component mappings take precedence. Frames use the mapper's allocated column count; this is not inferred semantic UI.
- Opaque terminal frames retain explicit descendant instances and project their original focus onto the correct xterm input. Frames without an input handler forward raw keys to Pi's focused component; original wrapper handlers keep priority without taking descendant focus. Raw input preserves Pi keyboard semantics, bracketed paste and xterm composition. Original listeners can redirect, consume or clear input focus; an explicit clear does not fall back to the first control. Unregistered closure-held focus projects when its surface has a single terminal. Ownership across multiple inaccessible regions and arbitrary presentation transitions remains unproven.
- `backend/terminal-queries.ts` routes factory `queryTerminalColors` through a separate renderer probe and an original Pi `TuiMainScreen` parser for each query. Foreground/background and all 16 palette entries come from the actual xterm, including OSC color changes. Options are captured synchronously, retaining original timeout/partial/late-reply behavior and bare late-callback invocation with an undefined receiver. Factory disposal retains pending queries; generation teardown clears their timers and prevents retired callbacks. `terminal.query.list` replays pending probes when the renderer connects or reconnects; `terminal.query.reply` routes responses without injecting them into the PTY.
- `src/terminal-io.ts` serializes renderer probes with PTY writes. It intercepts only OSC color/DA1 replies produced during a desktop probe; keyboard input and replies to PTY programs continue to the PTY. Queries do not open or focus the panel.
- Render-only frames translate Pi's `CURSOR_MARKER` to an xterm cursor position using original `visibleWidth`, scan the visible viewport from bottom to top, and honor `getShowHardwareCursor`. The original rendered arrays are retained without mutation.
- Render-only pointer input uses the shared original Pi mouse dispatch/retargeting bridge. DOM hit paths use actual xterm cell sizes and scroll offsets; terminal component widths remain their allocated render widths. Captured drags cross component boundaries, unhandled wheel input can fall back to original parents, and original focus requests reach xterm's input textarea. A native wheel capture listener prevents xterm from swallowing component wheel callbacks or duplicating parent dispatch.
- The `bash` desktop action emits Pi's original `user_bash` hook after the existing command confirmation, preserving extension-supplied results/custom operations and recording results with `recordBashResult`. The unchanged official `interactive-shell.ts` therefore executes through its own original handler. `SHELL` is preserved; if absent, the worker uses Pi's platform shell resolver.

## Limits

PTY compatibility requires the program and its shell to exist on the user's computer. Supported escape/keyboard/image protocols follow xterm.js and the platform terminal; not every terminal-specific extension is supported. Without a connected renderer, color queries follow Pi's timeout semantics and report only replies received, with pending late replies retained until completion or owner disposal. A bounded raw-output replay can omit older screen history and is not a serialized full terminal screen. Real-account provider/OAuth/MCP and physical OS IME/touch verification remain separate from terminal fixture coverage.

The SDK remains pinned to 1.0.0. This removes the need for a Pi fork, but desktop bridge tests are still required before SDK upgrades.
